# 📘 Comprehensive Notes: Jenkins Build Job with GitHub + Maven + Artifact Archiving

---

## 1. **Tools Setup in Jenkins**

* Go to **Manage Jenkins → Global Tool Configuration → Tools**
* Configure:

    * **JDK installations** (multiple versions: JDK17, JDK21, JDK11 if needed).
    * **Maven installations** (system default or custom versions like Maven 3.9).
* Why multiple versions?

    * Different projects may require different JDK or Maven versions.
    * Example: `vprofile` supports JDK17 and JDK21; another branch supports JDK11.

**👉 Real-life:**

* Always configure multiple JDK/Maven versions to handle different microservices in the same Jenkins instance.

**👉 Interview Tip:**

* *“How do you handle different JDK versions for multiple projects in Jenkins?”*
  → Answer: Configure multiple JDK tools under Global Tool Config and select the right one per job.

---

## 2. **Creating the Build Job**

* **New Item → Freestyle Project → Job Name (e.g., Vprofile-Build)**
* Provide **job description** (e.g., "Build artifact from vprofile source code").
* Select required **JDK version** (e.g., JDK17).

---

## 3. **Source Code Management (SCM)**

* Select **Git** and provide repository URL:

    * Example: `https://github.com/hkhcoder/vprofile-project`
* **Credentials:**

    * Public repo → no credentials needed.
    * Private repo → add credentials:

        * Username + password/token
        * SSH private key
        * GitHub App
        * Secret file/text/cert
* **Branch specification:** Select required branch (`main`, `atom`, or `jdk11`).

**👉 Real-life:**

* Always store credentials in Jenkins Credentials Manager instead of hardcoding.

**👉 Interview Tip:**

* *“How do you securely manage GitHub credentials in Jenkins?”*
  → Use Jenkins **Credentials Manager** and reference via dropdown in SCM.

---

## 4. **Build Steps (Using Maven)**

* Options:

    1. **Execute Shell** → run `mvn install`
    2. **Plugin: Invoke top-level Maven targets** ✅ (preferred)

        * Select Maven version (default/system/3.9)
        * Goals → `install`, `test`, etc.
        * Advanced options → specify custom POM, JVM options, properties.

**👉 Best Practice:**

* Always use plugins where available (easy configuration, more features, less error-prone).
* Only use `Execute shell` if no plugin exists.

---

## 5. **Build Execution & Logs**

* Jenkins downloads required Maven version if not installed.
* Console Output shows:

    * Tool setup
    * Commands executed
    * Build success/failure
* Common issues:

    * Missing Maven → "No such file or directory"
    * Wrong Maven version → Build/test failures

**👉 Real-life:**

* Always cross-check tool versions. Example: `vprofile` requires Maven ≥ 3.9; if only 3.8 is installed, tests fail.

---

## 6. **Post-Build Actions (Artifact Handling)**

* Example: **Archive the artifacts**

    * Pattern: `**/*.war` → archives all WAR files recursively.
* Workspace contains:

    * `target/vprofile-v2.war`
* Archived artifacts remain accessible even if workspace is wiped.

**👉 Real-life:**

* Use **artifact repositories** (e.g., Nexus, Artifactory, AWS S3) instead of storing in Jenkins.
* Jenkins artifact archiving is only for quick demos/testing.

**👉 Interview Tip:**

* *“Where should you store artifacts generated by Jenkins jobs?”*
  → In external artifact repositories, not Jenkins workspace.

---

## 7. **Error Handling**

* **Wrong Maven version → build fails**
* **System default Maven missing → job fails with "command not found"**
* **Java stack traces may be cryptic** → always scan full console output.

**👉 Real-life Debugging:**

1. Check console output
2. Verify Maven/JDK versions
3. Inspect workspace files
4. Retry with correct tool configuration

---

## 8. **Creating Experimental Jobs**

* Instead of recreating jobs:

    * Use **Copy from Existing Job** (e.g., copy Vprofile-Build → Vprofile-Test).
* Modify copied job:

    * Change Maven goals (e.g., `test` instead of `install`).
    * Remove/archive artifact step if not required.

**👉 Real-life:**

* Great way to test multiple configurations without disturbing production jobs.

---

## 9. **Exercise (Practice for Projects/Interviews)**

* Install JDK11 in Jenkins server:

  ```bash
  sudo apt update
  sudo apt install openjdk-11-jdk -y
  ```
* Add JDK11 in **Global Tool Configuration**.
* Create a job that:

    * Uses branch `JDK11` from repository.
    * Selects JDK11 as tool.
    * Runs `mvn install`.
* Ensure job builds successfully.

---

## 10. **Best Practices**

* Always document job description.
* Prefer plugins over shell commands.
* Use Jenkins Credentials Manager for secrets.
* Store artifacts in repositories, not Jenkins.
* Copy jobs for experiments instead of altering working jobs.

---

# 🎯 Interview-Ready Q\&A

**Q1:** Why do we configure multiple JDK/Maven versions in Jenkins?
➡️ Because different projects may require different versions. Jenkins lets us define them under Global Tool Configuration and choose per job.

**Q2:** How does Jenkins handle private GitHub repos?
➡️ By using stored credentials (username/token or SSH keys) in Jenkins Credentials Manager.

**Q3:** Difference between Execute Shell and Maven Plugin?
➡️ Execute Shell runs raw commands; Maven Plugin provides structured options and better maintainability. Always prefer plugin when available.

**Q4:** Where should Jenkins artifacts be stored?
➡️ In external artifact repositories (Nexus, Artifactory, S3) for versioning, scalability, and reliability. Jenkins workspace is temporary.

**Q5:** If Jenkins job fails with "command not found," what do you check?
➡️ Verify tool installation, ensure the selected Maven/JDK version is installed/configured in Global Tool Config.

# 📘 Jenkins Notes – Plugins, Variables, and Versioning

---

## 1. 🔌 **Jenkins Plugins**

Plugins extend Jenkins’ functionality and integrate with external tools/services.

### 📍 Accessing Plugins

* Navigate: **Manage Jenkins → Plugins**
* Sections:

    1. **Updates** → Plugins with new versions available.
    2. **Available Plugins** → Browse/search and install new plugins.
    3. **Installed Plugins** → View all installed plugins; can disable/uninstall some.
    4. **Advanced Settings** → Upload `.hpi/.jpi` plugin files manually (developed in-house or third-party).

### 📍 Example

* Search **S3** in *Available Plugins*.
* Install **S3 Publisher** plugin.
* This may auto-install dependencies (e.g., **AWS SDK::Minimal**).
* After installation, new options like **“Publish artifact to S3 bucket”** appear in job configurations.

⚠️ Note: Some plugins can’t be disabled directly if other plugins depend on them.

---

## 2. 🔑 **Variables in Jenkins Jobs**

Variables allow dynamic behavior in builds.

### 📍 Built-in Environment Variables

Some common built-in variables:

* `BUILD_ID` → Unique build number (incremental).
* `BUILD_URL` → URL of the build.
* `JOB_NAME` → Name of the job.
* `JAVA_HOME`, `JENKINS_URL`, etc.

Reference: [Jenkins Environment Variables](https://www.jenkins.io/doc/book/pipeline/jenkinsfile/#using-environment-variables).

---

## 3. 📦 **Artifact Versioning**

Artifacts (e.g., `.war`, `.jar`) need versioning to avoid overwriting.

### 📍 Approach 1 – Using `BUILD_ID`

1. Create a new Freestyle job (copy existing job).
2. Add **Execute Shell** step:

   ```bash
   mkdir -p versions
   cp target/vprofile-v2.war versions/vpro$BUILD_ID.war
   ```
3. Each build creates a unique version (`vpro3.war`, `vpro4.war`, etc.).

---

### 📍 Approach 2 – Using **Parameters**

* Configure Job → Enable **“This project is parameterized”**.
* Add **String Parameter**:

    * Name: `VERSION`
    * Default value (optional): e.g., `1.0.0`
* Modify shell script:

  ```bash
  mkdir -p versions
  cp target/vprofile-v2.war versions/vpro$VERSION.war
  ```
* On build: **Build with Parameters → Enter version (e.g., 2.3.6)**.
* Output: `vpro2.3.6.war`.

---

### 📍 Approach 3 – Using **Timestamps**

1. Install **Build Timestamp Plugin**.
2. Configure: **Manage Jenkins → Configure System → Enable Build Timestamp**.

    * Define custom format, e.g.:

      ```
      ddMMyy_HHmm
      ```
3. Use in job:

   ```bash
   mkdir -p versions
   cp target/vprofile-v2.war versions/vpro$BUILD_TIMESTAMP.war
   ```

* Each artifact has unique timestamped version (`vpro130925_1435.war`).

---

## 4. ☁️ **Storing Artifacts Outside Jenkins**

Artifacts should not be permanently stored in Jenkins (limited space). Instead, push to external repositories:

* **S3 Bucket** → Using **S3 Publisher plugin**.
* **Nexus / Artifactory** → For proper version management & Maven integration.

### Example: Post-Build Action

* Add **“Publish artifact to S3 bucket”** step.
* Provide:

    * **Source** → Path of artifact (`**/*.war`).
    * **Destination** → S3 bucket name.
    * **Credentials** or attach **IAM Role** with S3 access.

---

## 5. 📋 **Key Takeaways**

* **Plugins** = Extend Jenkins with integrations & custom functionality.
* **Variables** = Provide dynamic build behavior (built-in + custom parameters).
* **Artifact Versioning** = Essential for tracking builds; can use:

    * Build IDs,
    * Parameters (manual version input),
    * Timestamps (automated).
* **Best Practice** = Move artifacts out of Jenkins (S3, Nexus, Artifactory).

# 📘 Jenkins Notes – Handling Disk Space Issues

---

## 1. ⚠️ **Problem: Disk Space Issues in Jenkins**

* While running Jenkins jobs, you may encounter:

  ```
  no space left on device
  ```
* Causes:

    * Jenkins runs many jobs → **workspace grows large**.
    * Many **plugins** installed → consume disk space.
    * Default EC2 instance root volume → only **8 GB** (too small for real workloads).

---

## 2. 📍 **Steps to Resolve – Increase Disk Size in EC2 (AWS Jenkins Server)**

### 🔹 Step 1: Check Current Disk Usage

Log into Jenkins server (EC2 instance):

```bash
sudo -i     # switch to root user
df -h       # check disk usage
fdisk -l    # list partitions and disk size
```

* Example output:

    * Disk: `/dev/xvda` → 8GB
    * Partition: `/dev/xvda1` → \~7GB available

---

### 🔹 Step 2: Modify EBS Volume

1. Go to **AWS Management Console → EC2 → Instances → Select Jenkins Instance**.
2. Scroll to **Storage → Root Volume (8GB)**.
3. Click the volume ID → opens EBS Volume details.
4. Rename it for clarity (e.g., **JenkinsRootVolume**).
5. **Actions → Modify Volume** → Increase size (e.g., from **8GB → 20GB**).
6. Confirm **Modify**.

---

### 🔹 Step 3: Reboot the Instance

```bash
sudo reboot
```

Or via AWS Console:
**Instance State → Reboot**.

---

### 🔹 Step 4: Verify New Disk Size

After reboot, log in again:

```bash
sudo -i
fdisk -l     # shows disk now 20GB
df -h        # shows ~19GB available
```

✅ Now Jenkins has more space available for jobs, plugins, and artifacts.

---

## 3. 📋 **Key Notes**

* Default **8GB** is insufficient for Jenkins heavy usage.
* Better to increase to **20GB+** right away before running multiple jobs.
* Always monitor disk usage:

  ```bash
  df -h
  du -sh /var/lib/jenkins/workspace/*
  ```
* If needed, periodically **clean up old builds**:

    * Configure job → **Discard Old Builds** → keep only last N builds.
    * Or manually delete unused workspaces.

---

## 4. 🎤 **Interview Questions**

### ⚠️ Disk Space Issues

1. What common error do you see when Jenkins runs out of disk space?
   → *“No space left on device”*.

2. Why does Jenkins often run out of space on EC2 instances?
   → Small root volume (8GB by default), multiple jobs, large workspaces, many plugins.

3. How do you check available disk space on a Linux server?
   → `df -h` for usage, `fdisk -l` for partitions.

4. What’s the difference between **disk size** and **partition size**?

    * Disk size = total capacity of the attached volume.
    * Partition size = allocated portion of that disk for use.

5. How do you increase disk space for Jenkins running on AWS EC2?
   → Modify EBS volume size via AWS Console → Reboot instance → Verify with `df -h`.

6. Apart from increasing disk size, how else can you manage Jenkins disk usage?

    * Configure jobs to discard old builds.
    * Clean unused workspaces.
    * Archive artifacts externally (S3, Nexus).
    * Install only necessary plugins.

7. What’s the risk of filling Jenkins server disk completely?

    * Builds fail.
    * Jenkins may stop responding.
    * System instability.
